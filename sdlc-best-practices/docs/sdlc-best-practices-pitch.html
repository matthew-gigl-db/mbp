The problem

Data platforms fail the same way software used to.

Jobs edited in production, pipelines copied by hand between workspaces, schedules nobody owns, and a cloud bill no one can explain. These are not tooling gaps — they are missing lifecycle practices.

Drift

A UI edit in prod fixes tonight’s failure and silently diverges from what is in Git. The next deploy reverts it, or worse, nobody deploys again.

Personal identities in prod

Jobs run as the engineer who created them. When that person leaves or changes teams, production breaks — and access reviews cannot tell who should own what.

Untested changes

Without isolated dev and test environments, the first realistic run of a change is in production — against real data, on a schedule.

Unattributable spend

Resources created by hand carry whatever tags someone remembered. Finance asks “which product costs this?” and the answer is a spreadsheet exercise.

The goal

Everything that runs in production is defined in Git, reviewed in a pull request, tested in an isolated environment, deployed by a service principal, and tagged for cost — automatically. Declarative Automation Bundles make that the default path rather than a discipline every team must invent.

The catalog is the environment

Following the Unity Catalog naming conventions, schema and table names are identical in tst, uat, and prod; only the catalog changes. SQL, dashboards, and downstream consumers never need environment-specific edits.

Developers and pull requests are personalized automatically — dev_<you>_orders and pr42_orders — so concurrent work never collides.

Humans develop; service principals deploy

Engineers deploy only their own dev copy. Every shared target is deployed by a dedicated, per-environment service principal authenticated with GitHub OIDC — no stored secrets.

Production workloads run as a separate run_as service principal, so ownership survives team changes and access reviews map cleanly to groups.

Declarative Automation Bundles

What a bundle is — and what bundle deploy does for you.

A bundle is a folder in Git with a databricks.yml: your source code plus a declarative description of every Databricks resource it needs, for every environment. The Databricks CLI turns that description into a running data product.

repository layout
orders_bundle/
├── databricks.yml          # bundle, variables, artifacts, targets
├── resources/              # one file per deployable asset
│   ├── schemas/orders.schema.yml
│   ├── volumes/landing.volume.yml
│   ├── pipelines/orders_medallion.pipeline.yml
│   └── jobs/orders_refresh.job.yml
├── src/
│   ├── orders_lib/         # wheel: rules + quality gate
│   └── pipelines/orders_medallion/transformations/
│       ├── bronze_orders.py
│       ├── silver_orders.py
│       └── gold_daily_revenue.py
├── tests/test_rules.py     # pytest, no workspace needed
└── pyproject.toml

The complete, validated example lives in examples/orders_bundle.

databricks.yml (excerpt)
bundle:
  name: orders_bundle
  engine: direct
  databricks_cli_version: ">= 1.20.0, < 2.0.0"

include:
  - resources/*/*.yml

artifacts:
  orders_lib:
    type: whl
    build: uv build --wheel

targets:
  dev:
    mode: development
    default: true
    variables: { catalog: retail_dev }
  prod:
    mode: production
    variables: { catalog: retail }
    run_as:
      service_principal_name: ${var.run_as_service_principal}
    presets:
      trigger_pause_status: UNPAUSED
      tags: { project: ${var.tags_project}, env: ${bundle.target} }

Deep dive

The features that make bundles a lifecycle tool, not just a deployer.

  1. Deployment modes encode your environment policy

    mode: development prefixes every resource with [dev <you>], personalizes schemas, pauses schedules, marks pipelines as development, and tags resources with the developer. mode: production does the opposite: it refuses deploys from the wrong Git branch, rejects personal paths, and requires an explicit run_as and permissions.

  2. Presets apply cross-cutting rules per target

    name_prefix, trigger_pause_status, pipelines_development, artifacts_dynamic_version, and tags are set once per target and applied to every resource. Resource-level settings override presets; presets override mode defaults.

  3. Zero hardcoding with variables, substitutions, and lookups

    Resources reference ${var.catalog}, ${bundle.target}, and ${workspace.current_user.short_name} — never literal catalogs, hosts, or principals. Lookups resolve warehouses, policies, and service principals by name per workspace. CI sets any variable with BUNDLE_VAR_<name>.

  4. References give you dependency ordering for free

    pipeline_id: ${resources.pipelines.orders_medallion.id} and ${resources.schemas.orders_schema.name} wire resources together and tell the engine what to create first. Raw strings would compile but deploy in the wrong order.

  5. Identity and permissions are part of the definition

    run_as sets the workload identity; target-level permissions grant CAN_VIEW, CAN_RUN, or CAN_MANAGE to groups across every resource; schema and volume grants manage Unity Catalog privileges. Access is reviewed in the same pull request as the code.

  6. Production data is protected per target

    lifecycle: prevent_destroy: true on the prod schema and volume means neither bundle destroy nor an accidentally deleted YAML block can drop production data — while dev and PR copies remain fully disposable.

  7. Ship exactly what was reviewed

    bundle plan -o json > plan.json captures the change set; a reviewer approves it; bundle deploy --plan plan.json applies that plan and nothing else. Combined with --fail-on-active-runs, production changes are predictable.

  8. Adopt what you already have

    bundle generate turns an existing job, pipeline, dashboard, or app into bundle YAML; bundle deployment bind attaches the bundle to the live resource so it is updated in place instead of duplicated. Brownfield migration is incremental.

  9. Scale conventions with templates and Python

    databricks bundle init starts from built-in or organization templates so every team inherits the same targets, tags, and CI wiring. Python bundles add mutators — functions applied to every job or pipeline — to enforce required tags, notifications, or serverless compute centrally.

Bundles are only for jobs
Pipelines, dashboards, apps, Genie spaces, serving endpoints, UC schemas and volumes, grants, warehouses, and Lakebase are all bundle resources.

Clicking in the UI is faster
For the first deploy, maybe. bundle deploy to your dev target takes seconds, and every later environment is free — with review, rollback, and audit included.

FinOps by default

Tag once in the bundle. Attribute every dollar.

Cost allocation fails when tagging is a manual step. In a bundle, tags are a target preset: every taggable resource the bundle deploys inherits them, in every environment, on every deploy.

A small, mandatory tag taxonomy

projectorders-medallion businessUnitRetail Analytics costCenterCC-0000 ownerdata-engineering env${bundle.target} pullRequestci only
  • ✓Owners are teams, never individualsPeople move; cost centers and groups persist.
  • ✓env comes from the target${bundle.target} cannot be mistyped and splits dev, test, and prod spend automatically.
  • ✓Values are variables, defaults in one placeDeclared in databricks.yml, overridable per target or by BUNDLE_VAR_* in CI.
  • ✓Developer copies are identifiableDevelopment mode adds the deploying user, so stale dev deployments are easy to find and clean up.

Report spend by product and environment

sql
SELECT
  u.custom_tags['project']    AS project,
  u.custom_tags['costCenter'] AS cost_center,
  u.custom_tags['env']        AS env,
  u.billing_origin_product    AS product,
  ROUND(SUM(u.usage_quantity
    * lp.pricing.effective_list.default), 2) AS list_cost_usd
FROM system.billing.usage AS u
JOIN system.billing.list_prices AS lp
  ON  u.sku_name   = lp.sku_name
  AND u.cloud      = lp.cloud
  AND u.usage_unit = lp.usage_unit
  AND u.usage_end_time >= lp.price_start_time
  AND (lp.price_end_time IS NULL
       OR u.usage_end_time < lp.price_end_time)
WHERE u.usage_date >= current_date() - INTERVAL 30 DAYS
GROUP BY ALL
ORDER BY list_cost_usd DESC;

Close the loop

  • ✓Track untagged spend as a KPIFilter the same query on custom_tags['project'] IS NULL. Anything deployed outside a bundle shows up here first.
  • ✓Enforce tags before deployA Python mutator or a CI check fails the pull request when a required tag is missing — no tag, no merge.
  • ✓Budget per cost centerAccount budgets and alerts filter on the same tag keys the bundle sets.
  • ✓Clean up what dev leaves behindPer-PR deployments are destroyed when the PR closes; dev copies are tagged with their developer for periodic review.
Billing tags vs. governed tags

Compute and workload tags drive cost attribution. Unity Catalog governed tags on tables and columns drive data classification and access policy. Use both, with separate, documented taxonomies.

Workload identity federation

Each GitHub environment (ci, tst, uat, prod-plan, prod) federates to exactly one deploy service principal. The job requests a short-lived GitHub OIDC token; the CLI exchanges it for a Databricks token. Nothing to rotate, nothing to leak.

_deploy.yml
jobs:
  bundle:
    environment: ${{ inputs.environment }}
    env:
      DATABRICKS_AUTH_TYPE: github-oidc
      DATABRICKS_HOST: ${{ vars.DATABRICKS_HOST }}
      DATABRICKS_CLIENT_ID: ${{ vars.DATABRICKS_CLIENT_ID }}
      BUNDLE_VAR_run_as_service_principal: ${{ vars.RUN_AS_SERVICE_PRINCIPAL }}
    steps:
      - run: databricks current-user me    # prove federation first
      - run: databricks bundle validate --strict -t ${{ inputs.target }}
      - run: databricks bundle deploy --plan plan.json --fail-on-active-runs

Hardening that comes with the pattern

  • ✓Federation policy bound to a GitHub environmentSubject repo:<org>/<repo>:environment:prod — branch rules and reviewers on that environment guard production credentials.
  • ✓Plan, then approve, then applyprod-plan publishes the plan to the run summary; prod applies that artifact after a required reviewer approves.
  • ✓Least-privilege tokenscontents: read by default; id-token: write only on deploying jobs.
  • ✓Pinned supply chainActions pinned to full commit SHAs; CLI version pinned in the workflow and constrained in databricks.yml.
  • ✓Queued, not cancelled, releasesConcurrency groups serialize deploys per target.
  • ✓Fork code never sees credentialsNo pull_request_target; fork PRs run unit tests only.

Quality and release

Test in layers. Release by commit. Roll back by tag.

every commit

Unit tests

Business rules live in a Python package (orders_lib) and are tested with pytest — no workspace, seconds to run. The same package is built into the wheel the job uses.

every pull request

Deploy and validate

bundle validate --strict, a real deploy to an isolated ci target, and a pipeline --validate-only run that checks the dataflow graph without processing data.

every merge

Integration tests

Deploy to tst, seed fixture data into the landing volume, run the job end to end, and fail on the data quality gate.

Promotion

  • ✓Trunk-basedmain is always deployable; short-lived feature branches.
  • ✓Same commit, every environmentNo rebuilds or edits between tst, uat, and prod.
  • ✓Release tagsEvery production deploy tags its commit — the tags are your rollback catalog.

Rollback

Run the CD workflow with ref set to the last good release tag. The same tests, plan, and approval apply — rollback is just another reviewed deploy.

Code vs. data

Redeploying code does not roll back data. Use Delta time travel or RESTORE for tables, and prevent_destroy so a bad deploy can never drop them.
