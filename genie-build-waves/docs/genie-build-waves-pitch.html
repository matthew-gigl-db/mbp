Overview

What is Genie Build Waves?

Genie Build Waves is a Databricks Declarative Automation Bundle that decomposes any large project into dependency-ordered waves of parallel Genie Code sessions. Each wave runs sessions concurrently, integrates results, and passes through a deterministic gate before the next wave begins. If a gate fails, every downstream wave is instantly excluded — zero compute wasted on a known-bad state.

Deploy the bundle once per workspace. Point it at any project's waves.json manifest. The setup job reads the manifest and generates a full task graph dynamically — no hardcoded waves in YAML. This means projects with two waves and projects with twenty waves both work without any bundle configuration changes.

Value Proposition

Why Genie Build Waves is valuable

Large Databricks projects share a common bottleneck: they are too big for a single Genie Code session to hold in context, but too interdependent to parallelize naively. Genie Build Waves solves this with structured parallelism, ownership boundaries, and deterministic gates — turning a sprawling build into a managed, observable pipeline.

  • ✓
    Parallelism without conflict Each session owns its paths or assets. The framework enforces non-overlapping owned_paths within a wave, so concurrent file edits never collide. The integrator is the sole committer — sessions never run Git write commands.
  • ✓
    Deterministic quality gates Every wave ends with a gate notebook that reads session status files and checks assertions independently. Gates are human-readable text the integrator interprets: “bundle validate --strict passes”, “table X has >0 rows”, “notebook Y ran without errors”. For convergence waves, the gate also checks deployment state, soak stability, and OTel error lines.
  • ✓
    Zero-compute cascade failure If a gate fails, an If/else condition task excludes all downstream wave tasks instantly. No Genie Code sessions spin up on a known-bad state. This keeps costs predictable and focuses debugging on the wave that actually broke.
  • ✓
    Repair-friendly Failing sessions leave their code uncommitted; passing sessions are already committed. Repair re-runs only the failed wave's tasks. Earlier waves show as skipped or already-completed — they re-validate idempotently.
  • ✓
    Two-phase build lifecycle Initial builds use wide, parallel edit waves to get breadth quickly. Follow-up convergence waves deploy, read telemetry, fix issues, and redeploy until stable. A passing stable build — deployed, running, clean logs — is part of the pass criteria, not just “files exist”.
  • ✓
    Generic and reusable One bundle per workspace. Project-specific values pass as --var flags at deploy time. The bundle's databricks.yml stays generic. Multiple projects share the same deployed bundle via instance_suffix — each gets its own deployment state, jobs, and automations.
The AI Engine

Why Genie Code for building in Databricks

Genie Code is the AI assistant built into Databricks. It reads and writes notebooks, queries, dashboards, and files in your workspace. It executes SQL, Python, and shell commands on your serverless compute. It understands Databricks-specific concepts — Unity Catalog, Lakeflow Jobs, Declarative Automation Bundles, Spark Declarative Pipelines — out of the box, without prompt engineering or context window management on your part.

Native Databricks context

Genie Code already knows your workspace, your tables, your schemas, your bundles, and your jobs. No API setup, no token management, no context window stuffing. It reads the same files you see in the workspace browser.

Serverless execution

Sessions run on serverless compute — no cluster provisioning, no cold starts. Genie Code executes SQL, Python, and shell directly. The build framework leverages this for execute and configure sessions that create resources as part of the build.

Skills as reusable prompts

The bundle publishes two UC Skills — a session runner and a wave integrator — that provide structured prompts for each Genie Code task. Skills are versioned, stored in Unity Catalog, and invoked by the job's genie_task entries. Change a skill and re-run setup; every session picks up the new prompt.

SDK & CLI native

Genie Code runs the Databricks SDK and CLI natively. The setup notebook uses the SDK to publish skills, create automations, and generate the job task graph via jobs/reset. Convergence sessions use the CLI to bundle deploy and the Apps API to verify deployment status.

Key insight

Genie Code is the build worker. Each session in a wave is a Genie Code task — a scheduled insight that receives a session plan, reads the manifest, implements within its owned paths, validates, and writes a status JSON file. The framework provides the structure; Genie Code provides the intelligence.

Best Practices

Working with the framework

Genie Build Waves is a powerful orchestration tool, but it is not a substitute for good design. The framework executes your plans — it does not write them. Following these practices will make your builds faster, safer, and more maintainable.

  1. Use Declarative Automation Bundles in Git Folders

    The bundle and the project being built are separate Git folders. The bundle orchestrates; the project is what gets built. Deploy the bundle once per workspace using --var flags — never edit databricks.yml with project-specific values. This keeps the bundle generic and reusable across any number of projects.

    /Workspace/Users/you@example.com/ ├─ genie-build-waves/ ← this bundle (deployed once per workspace) └─ my-project/ ← the project being built (separate Git folder)

  2. Use the Databricks AppKit and manual CLI for app bundle creation

    When your build target is a Databricks App, create the app bundle manually using the Databricks CLI (databricks apps create) or the AppKit scaffold flow. Do not let a build-wave session auto-scaffold an app from scratch — the framework is designed to build on top of a well-structured existing bundle, not to invent one. The converge session deploys and verifies, but the bundle itself should exist before the build starts.

  3. Curate your designs before using this package

    The most common failure mode is feeding Genie Build Waves an under-designed project. The framework decomposes and parallelizes — it does not architect. Before writing your waves.json, invest in:

    • Architecture documents — What are the components, their boundaries, and their dependencies?
    • API contracts — What interfaces do components expose? Define schemas, endpoints, and data shapes upfront.
    • Session plans — Each plan file must have numbered tasks, scope, and acceptance criteria. Vague plans produce vague sessions.
    • Ownership boundaries — Know which files belong to which session. Path overlap within a wave causes conflicts.
    • Gate criteria — Define what “done” means for each wave. Write gates as assertions, not aspirations.

    A well-curated design with 16 sessions across 6 waves will outperform a vague design with 40 sessions across 10 waves every time. The planner skill (in the bundle repo) can help with decomposition, but the quality of the input determines the quality of the output.

  4. Keep sessions small and focused

    Each session should complete one plan file with a clear scope. If a session tries to do too much, it will run long, lose context, and produce incomplete work. The framework's owned_paths enforcement helps here — if you cannot describe the ownership boundaries cleanly, the session is too big. Split it.

  5. Use instance_suffix for every project

    The instance_suffix variable is appended to the bundle root path, giving each project its own deployment state, jobs, and automations. Without it, deploying for a second project replaces the first project's jobs. Use a consistent suffix like -my-app every time you deploy or validate for a given project.

  6. Separate initial builds from convergence

    Initial builds use wide, parallel edit waves to get code breadth quickly. Convergence waves are sequential, one session per wave, and include deterministic runtime gates that check deployment state, soak stability, and OTel error lines. Do not mix deploy sessions into parallel waves — the setup job rejects any wave where a deploying session shares with another session.

  7. Never put the build job in the bundle being converged

    If a converge session deploys a bundle that also defines the build-waves job, the deploy will reset the running build job mid-flight. Keep the orchestration in the genie-build-waves bundle. The project being built should not reference the build job's resources.

  8. Add .build-status/ to .gitignore

    The status directory is per-run and ephemeral. It contains session status files, gate JSON, and runtime gate results. In git/hybrid modes, it must be git-ignored to prevent the integrator from accidentally committing build artifacts.

Safety

Guardrails

The framework enforces structural safety rules so that parallel sessions cannot step on each other or on your infrastructure.

No path overlap

In git/hybrid modes, two edit-mode sessions in the same wave must not have overlapping owned_paths. This prevents merge conflicts when sessions run in parallel.

Sessions are Git read-only

Only the integrator commits, by explicit path, to a feature branch. Sessions never run Git write commands. main/master are refused as branch targets.

Single-writer deploys

A wave containing a converge or allow_deploy session must have exactly one session. The setup job rejects manifests that break this rule.

Deterministic runtime gates

The gate notebook checks deployment state directly — it does not trust session or integrator reports. It queries the Apps API, Jobs API, and OTel tables itself.

No suppression hiding

converge sessions must fix causes, not hide them. Any test skip, compile exclude, @ts-ignore, or swallowed error must be listed in the status file and is surfaced in the gate output.

Build job isolation

Never put the build-waves job in the bundle a converge session deploys. The deploy would reset the running build job mid-flight. Keep orchestration in the genie-build-waves bundle.
